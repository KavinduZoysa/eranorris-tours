# eranorris-tours

Map-first website for private tours of Sri Lanka, implemented from the Claude Design export
(`design/design-source.html`). It is a static site: plain HTML pages generated by a small
Node build, a single deferred script for the interactive map and planner, and no server.

```bash
npm ci
npm run dev             # local preview at http://localhost:4173 (noindex, drafts visible)
npm test                # preview build (drafts shown) + checks, then production test build + checks
npm run build:staging   # noindex everywhere, robots "Disallow: /", drafts visible
SITE_URL=https://www.your-domain.com npm run build   # real production build
npm run check:release   # launch gate: also fails on unconfirmed business details
```

## Build modes and safeguards

| Command | Indexable | Domain | Drafts shown | Can be released |
|---|---|---|---|---|
| `npm run build` | published pages only | `SITE_URL` **required**; placeholders refused | no | yes, if `check:release` passes |
| `npm test` | as production | reserved `tours.example.test` | no | never (recorded as a test build) |
| `npm run build:staging` | nothing | any | yes | never |
| `npm run dev` | nothing | `http://localhost:4173` | yes | never |

- **Domain checks.** A production build stops with an explanation if `SITE_URL` (or `url` in
  `site.config.mjs`) is missing, isn't `https`, or uses a placeholder hostname such as
  example.com, `.test` or `localhost`. Every canonical, sitemap, Open Graph and
  structured-data URL is generated from that one value, and `npm run check` verifies they
  all agree.
- **Content checks.** The build also stops on invalid content files:
  - an unknown `status` value, or a published page that is too short or still contains
    `[TODO]`
  - unknown destination ids, or an incomplete tour price
  - example pages in a production build
- **Release gate.** `npm run check:release` runs in the deploy workflow. It fails unless this
  is a real production build and every item under `confirmed` in `site.config.mjs` is
  `true`.

## Launch checklist

Nothing below has been invented in the site. Values that came from your villa site
(eranorrissrilanka.com) or from the design prototype are shown so you can check them. Mark
each one `true` under `confirmed` in `site.config.mjs` once checked.

**Domain and hosting (required)**

1. **Choose the address and set `SITE_URL`.** Decide whether the site lives at the root of a
   domain (`https://www.your-domain.com`) or in a sub-directory
   (`https://www.your-domain.com/tours`). Set `SITE_URL` to exactly that, and add it as a
   repository variable for the deploy workflow.
2. **One canonical hostname.**
   - Redirect the other variant (www ↔ apex) and all `http://` URLs to it with HTTP 301.
   - On GitHub Pages: add both DNS records, set the custom domain and tick "Enforce HTTPS".
   - On Netlify or Cloudflare Pages: set the primary domain and enable HTTPS redirects.
3. **Sub-directory only:**
   - Put a `robots.txt` at the domain root containing `Sitemap: <SITE_URL>/sitemap.xml`.
   - Make sure the host serves `<path>/404.html` for missing pages under that path.

## What changed from the design export, and why

The colours, type, map styling and markers are kept as designed. The planner's flow was later
reshaped into a guided, step-by-step journey (see [Guided trip planner](#guided-trip-planner)).
Other changes were made only for function, SEO, accessibility or performance:

- **Photos fill the design's empty image slots** (map medallions and destination card). That
  is the slot's intended filled state.
- **Brand**: the design's placeholder name → "Eranorris" (see above). The favicon uses the design thumbnail's
  terracotta circle with an "E".
- **Real request hand-off**: the design's form showed a "sent"/"booked" confirmation without
  sending anything. It now sends the full trip summary to WhatsApp/email (or `QUOTE_ENDPOINT`),
  and the confirmation only claims what actually happened.
- **Crawlable content**: a "Places you can add…" section and a footer below the planner list
  every destination as a real link. The destination dialog gains a "More about X →" link.
- **Accessibility**:
  - Markers are focusable, named, and open with Enter/Space.
  - The search fields are ARIA comboboxes; filter chips expose their pressed state.
  - Dialogs trap and restore focus; form errors are announced and focus the field.
  - Toasts are a live region, focus outlines are visible, and reduced motion is respected.
  - One design colour was darkened slightly to reach 4.5:1 contrast.
- **Resilience**: if JavaScript is off or the map script fails, the page says so and points
  to the place list and WhatsApp; `localStorage` failures no longer break the planner.
- **Honest expectations**:
  - Drive times, distances and transfer pickup times are labelled as estimates.
  - Airport transfers are *requested*, not "booked" (there is no availability system), and no
    price is shown: the guest gets a quotation.
  - The form says up front when a request will be sent through WhatsApp or email.
  - Saved trips with past dates are cleared, so no request can go out for a date that has
    passed.
- **Performance**: no third-party requests at all.
  - Leaflet and the map geometry are bundled/self-hosted. The ~750 KB world-atlas download
    and topojson are replaced by a 15 KB pre-extracted file.
  - The design's Google Fonts files are self-hosted and preloaded.
  - CSS is inlined, and the planner's initial state is pre-rendered (no layout shift).
  - Images are AVIF/WebP at several sizes, with lazy loading below the fold.

## Main page: two services

The main page offers two services as two equal cards over the map:

| Card | Text | Button | Opens |
|---|---|---|---|
| **Plan Your Sri Lanka Tour** | "Discover amazing places, explore experiences and build your own personalised private tour." | Plan My Tour | the [guided trip planner](#guided-trip-planner) |
| **Airport Shuttle & Private Transfers** | "Need a comfortable transfer? Choose your pickup and drop-off locations and request your private transfer." | Book Airport Transfer | the [airport shuttle](#airport-shuttle) |

- **One page, three views.** `<html data-svc>` says which is showing: no attribute = the main
  page, `tour` = the tour planner, `sh` = the airport shuttle. `src/js/app.js` sets it
  (`S.mode`), and `src/styles/app.css` shows one view from it. One map and one script serve all
  three.
- **A switch stays on screen** inside each service ("Tour planner | Airport shuttle"), so the
  other one is always one press away. The site menu has both too (`/#tour`, `/#transfer`).
- **Coming back:** a visitor with a trip or a transfer in progress returns straight to it; so
  does anyone following a link such as `/#add=kandy` or `/#transfer`. A small inline script
  (`SVC_BOOT` in `src/templates/home.mjs`) decides this before the first paint, so the cards
  never flash by. Everyone else sees the two cards.
- **The pictures on the cards** are drawn from what the map already uses (four place photos
  with stop numbers; the airport marker, A and B with the dotted route). No new images.
- **Separate state.** The tour keeps `S.stops`, `S.pickup`, `S.exps`, `S.start`, `S.adults`,
  `S.children`; the transfer keeps `S.tr`. Neither service reads or writes the other's, and
  each marks only its own choices on the map. "Clear" in one leaves the other alone.

## Airport shuttle

A transfer has exactly two locations: a pickup (A) and a drop-off (B). No stops, no
activities, no vehicle choice, no price.

| Step | What the visitor sees | Where it is |
|---|---|---|
| 1. Start | "Where would you like to go?", one instruction, and one card with two lists: **Pickup location** and **Drop-off location**. | `#tcard` |
| 2. Choose | Each location comes from its list, or from the map: a marker opens the place dialog with **Set as pickup** / **Set as drop-off** (nothing is chosen until one is pressed). The map shows A, B and a line between them. A swap button changes them over. | `#tFrom`, `#tTo`, `#dcard` |
| 3. Summary | With both chosen, the card says "CMB Airport to Galle: about 4h 40m, 185 km (estimate)" and the map zooms to the transfer. **Continue**. | `#tSum` |
| 4. Details | Travel date and pickup time (both may be left empty), passengers, name, email, WhatsApp/phone; optional flight, luggage and notes. A and B stay in view. **Edit locations** / **Review request**. | `#mbg`, `openTrDetails()` |
| 5. Review | "Your Airport Transfer Request": everything in one list. **Edit details** / **Request Airport Transfer**. | `#mbg`, `openTrReview()` |

Rules that the code and tests keep:

- **The places** are `TRANSFER_PLACES` in `src/data/destinations.mjs`: the two airports,
  Colombo, Negombo and the cruise terminal (from `PICKUPS`), then the 16 destinations
  ("hotels in and around …"). Airports come first in the lists and are on the map. "Somewhere
  else" drops a pin, for either end. No place was added for this.
- **Only two, never the same.** Choosing for one end the place that is already the other end
  makes the two change places. A third place can only replace one of them.
- **"Continue" needs both.** If one is missing it says which, and puts the visitor on it.
- **No vehicle and no price.** The request names a suggested vehicle for the number of
  passengers, to be confirmed. The guest is told we will confirm availability and send a
  quotation, and that nothing is booked until they confirm.
- **Airport advice** uses the confirmed timings (`SHUTTLE_TIMING`): for an airport pickup, "your
  driver waits for you in the arrivals hall"; for a drop-off at an airport, "we suggest
  reaching the airport 3 hours before it leaves".
- **Sending** works as for a tour (see below). With `QUOTE_ENDPOINT` the JSON has
  `type: "airport-transfer"` (a tour has `type: "tour"`) and a `transfer` object: `pickup` and
  `dropoff` (`id`, `name`, `lat`, `lng`), `date`, `time`, `passengers`, `flight`, `luggage`.
  The other fields are the same as before (`ref`, `name`, `email`, `phone`, `notes`,
  `message`, …). Success says "Thank you! Your transfer request has been sent."
- **Layout:** on wide screens the card sits beside the map. On stacked layouts (≤ 1100 px, and
  phones held sideways) the card comes first and the map is a block of its own under it, so
  the map never takes over a small screen and the whole island always fits in it.

## Guided trip planner

The tour planner leads a visitor through one step at a time. The steps are only different
views of one saved state (`S` in `src/js/app.js`, stored in the browser as `eranorris-trip-v1`).

| Step | What the visitor sees | Where it is |
|---|---|---|
| 1. Start | The map, the heading "Let's plan your Sri Lanka experience." and one instruction. Markers pulse softly twice. No trip panel, no open place. | `.overlay`, `#guide` |
| 2. Explore | Choosing a marker (or a search result) opens the place as a dialog: photo, text, facts, "Things to do" with tick boxes, **Add to my trip** and **Close**. | `#dback > #dcard` |
| 3. Trip | After "Add to my trip" the dialog closes, a message says "Kandy added to your trip!", and the compact trip panel appears: starting point, numbered places, **+ Add another destination**, **Finish planning**. | `#trip` |
| 4. Review | "Your Sri Lanka trip is taking shape!": starting point, places in order with nights and chosen experiences, drive estimates, **Edit my trip** / **Continue**. | `#mbg`, `openReview()` |
| 5. Details | Start date (optional), guests, name, email, WhatsApp/phone, **Send my trip request**. | `#mbg`, `openDetails()` |

Rules that the code and tests keep:

- **Opening or closing a place never changes the trip.** Only "Add to my trip" does. Experiences
  ticked in the dialog of a place that isn't in the trip wait (`draft` in `app.js`) and are
  kept only when the place is added. For a place already in the trip, ticks apply at once.
- **No duplicates:** a place in the trip shows "In your trip" and "Remove from my trip".
- **Starting point ≠ places to visit.** The starting point is `S.pickup` (where the trip begins
  and ends); the places are `S.stops`. The first place added is never taken as the starting
  point. "Finish planning" asks for the starting point if it is missing and puts the visitor
  on that field. "Or drop a pin on the map" covers places that are not in the list.
- **The guidance line** (`#guide`) changes with the state: choose a place → "Great! Now select
  another destination, or set your starting point." → "…choose Finish planning…".
- **The trip panel stays small:** names, nights and a count of experiences. Places can be
  moved earlier or later, removed, or put in the shortest order. It can be closed and reopened.
  On wide screens it floats over the right of the map; on stacked layouts (≤ 1100 px) it is a
  drawer along the bottom of the map and the zoom buttons move up above it.
- **No vehicle choice.** The request suggests the smallest vehicle that fits the group
  ("Vehicle: Van (suggested for the group size, to be confirmed)"). The fields sent to
  `QUOTE_ENDPOINT` for a tour are unchanged.
- **The request is honest:** with `QUOTE_ENDPOINT`, the button shows "Sending…", a second
  press is ignored, and success says the request was sent and that nothing is booked yet. A
  failure keeps the form and offers WhatsApp. Without an endpoint, the last screen offers
  WhatsApp or email and says nothing is sent until the visitor presses send there. What was
  typed is kept (in memory only) if the dialog is closed or a step is revisited.
- **Deep links:** `/#tour` opens the planner; `/#add=<id>` adds the place and shows the trip
  panel; `/#place=<id>` opens its dialog; `/#experiences=<id>` and `/#exp=<experience id>`
  open it at "Things to do".
- **Without JavaScript** (or if the script fails) the main page still shows both service
  cards (without their buttons), a note with WhatsApp and email links, and the place list.

## Mobile and desktop behaviour

Tested at 280–2560 px wide, portrait and landscape, with touch and mouse.

- **Phones (portrait)**:
  - The map fills the screen under the header. A place opens as a sheet from the bottom
    (nearly full height); its content scrolls on its own, "Add to my trip" and "Close" stay in
    reach, and the page behind does not scroll.
  - The trip is a one-row drawer at the bottom of the map ("Your trip · 2 places" and "Finish
    planning"); it opens to show the starting point and the places. The header's "Your trip"
    button jumps back to it from anywhere on the page.
  - Once a place is in the trip, the big heading is hidden (it stays in the page for screen
    readers) so the island and the drawer both fit.
  - The filter chips form one swipeable row.
  - One-finger swipes scroll the page; two fingers pan and pinch the map (a short hint
    says so). Taps on places, the starting-point pin and double-tap zoom work as usual.
- **Phones (landscape)**: the overlay sits on the left, as on desktop; the trip is a small
  card on the right, and the place dialog uses nearly the whole screen.
- **Tablets and desktop**: the map has the full width, with the search on the left and the
  trip panel floating on the right once a place is added. The place dialog is centred over a
  dimmed map. The mouse wheel zooms the map as designed.
- **Touch screens in general**:
  - Form fields are 16 px, so iOS doesn't zoom in when one is tapped.
  - Small controls have larger invisible tap areas.
  - Hover effects don't "stick" after a tap.
  - Instructions say "Tap" instead of "Click", and the dialog's close button stays visible
    while the dialog scrolls.
- **Map framing**: the map's pan limits were widened so the island always fits beside or
  below the overlay. The design's tighter limits hid places under the search box and chips
  on small or short screens.

## Experiences ("Things to do")

Each destination can list experiences: things a traveller can do or visit there. Visitors
pick the ones they like, and the choices go into their quote request. Picking one is not a
booking, and nothing is part of a tour unless you confirm it.

Every experience has a **kind**: a *main attraction* of the place, an *activity* there, or a
*nearby excursion* that needs extra travel (excursions always say where they are and roughly
how far). Cards are listed in that order and labelled with it; on destination pages they are
grouped under those headings. Who provides an experience isn't shown: all of them are arranged
through partners (owner, November 2026), and guests don't need that detail.

- **Map:** the destination dialog has a "Things to do in X" list (open by default,
  collapsible) with a checkbox per experience. It works with mouse, touch and keyboard (Space
  toggles). Choosing an experience never adds, removes or reorders a stop, and never moves
  the map. The airport shuttle shows no experiences.
  - For a place that isn't in the trip yet, ticks are kept only when the visitor presses "Add
    to my trip". "Close" drops them: closing never adds anything.
  - For a place already in the trip, a tick applies at once.
- **Trip panel:** shows only a count per place ("2 nights · 1 experience").
- **Review step:**
  - Chosen experiences appear under their place, each with a × to remove it.
  - Experiences at places that are no longer in the route are kept under "Also interested in ·
    places not in your route", with an "Add … to my trip" button. Removing a place never
    discards its experiences, and the message says so.
  - "Clear trip" (in the trip panel) asks first, then empties everything.
- **Saved with the trip:** selections are stored in the browser with the rest of the trip.
- **Quote request:** the summary and the WhatsApp/email message list experiences under
  each destination, plus an "Also interested in (not in the route yet)" group. With
  `QUOTE_ENDPOINT` set, the JSON also has an `experiences` array grouped by destination.
- **Destination pages:** they list the experiences in plain HTML (crawlable) with the
  fuller `details` text, and link to `/#experiences=<id>`, which opens the map dialog with the
  list expanded. No structured data is added for experiences.
- **Map bundle:** the app gets a trimmed copy of the data (no `details`, `source` or
  `imageAlt`), generated by the build, so longer card text doesn't slow the map down.

**Adding or editing an experience:** edit `EXPERIENCES` in `src/data/experiences.mjs`. The
field list is documented at the top of that file. For example:

```js
{
  id: 'galle-fort-sunset-walk',   // unique, kebab-case; it's saved in visitors' trips, so don't rename it
  destinationId: 'galle',         // an id from DESTS
  kind: 'activity',               // attraction | activity | excursion (an excursion needs `where`)
  category: 'history',            // a key of EXP_CATS
  name: 'Sunset walk on the ramparts',
  shortDescription: 'Only facts you can stand behind (≤ 200 characters; shown on the map).',
  details: 'Fuller card text for the destination page: general facts, typical times in words.',
  // where: 'Koggala, about 20 minutes east of Galle',   // where it is, if not in the place itself
  // duration: '2 hours',         // optional, only a duration you've confirmed for your offer
  // price: 'US$ 20 per person',  // optional, only a verified current price
  // image: 'galle-sunset', imageAlt: '…',   // optional: src/images/experiences/galle-sunset.jpg
  // featured: true,              // optional: listed first and marked "Featured"
  // available: false,            // optional: hide without deleting
  source: 'eranorrissrilanka.com',
},
```

The build stops on an unknown destination, a duplicate or badly formatted id, an unknown
category, kind or source, an excursion without `where`, a short description over 200
characters, or a missing image or alt text. `npm run check` confirms every experience is
listed on its destination page with its kind. To add photos, put a JPEG in `src/images/experiences/`, or map it in
`EXPERIENCE_PHOTO_SOURCES` (villa-site path, or `tours:<path>` for the tour album) and run
`npm run prepare:images -- --only=<name>`.

## Destination guides, experience guides and tours

**Destination guides** (`/places/<id>/`) exist for all 16 places. Each page has:
- breadcrumbs and a photo gallery
- the at-a-glance facts
- the guide itself: overview, sights, practical advice, length of stay, best time, getting
  there, and an FAQ
- the "Things to do" cards (selectable on the map)
- official links
- "Plan a private tour with …" with planner deep links (`/#add=<id>`, `/#place=<id>`)
- related tours
- "Nearby places to combine", chosen for real routes, with qualified times

The guide text lives in `src/content/places/<id>.md`. Each one was researched online; the
sources, verified facts and open questions are in `docs/research/<id>.md`.
**`docs/content-guide.md`** explains the format and the writing standard, with Kandy as the
reference.

**Experience guides** (`/experiences/<slug>/`) are kept for activities with their own search
intent and enough to say: so far the Temple of the Sacred Tooth Relic and Mirissa whale
watching. They live in `src/content/experiences/<slug>.md` and link back to their
destination. The "Choose it on the map" button (`/#exp=<experience id>`) opens the planner
with that experience in view.

**Galleries:** `src/data/galleries.mjs` maps each destination to extra photos after its main
photo. Only the business's own photos are used, and only where the subject and place are
identifiable. Places with one photo show no controls. The gallery is a swipeable strip with
previous/next buttons, a counter, dots and arrow keys (`src/js/gallery.js`, part of the
2 KB page script), and it works without JavaScript. Gaps and the photos to confirm are in `docs/research/photos.md`.

**Publishing rules.** Every guide is a **draft** until the owner signs it off. Drafts are
`noindex`, out of the sitemap, and their text appears only in staging/development previews.
In production a draft destination page shows just the design summary, photos, experiences
and planner links, and draft experience guides and tours aren't built. To publish, the build
requires:
- `status: published`
- a `reviewed:` date
- no remaining `verify:` items
- no `[TODO]`/`TBD`
- at least 200 words (120 for experience guides and tours)
- internal links that point at real, published pages

Preview with `npm run build:staging && npm run serve`.

**Tours** (`/private-tours/<slug>/`) come from `src/content/tours/<slug>.md`, documented in
`_example-sigiriya-private-tour.md`. Only fields you fill in are shown or added to the
`TouristTrip` structured data. Published tours are linked from the destinations they visit.

## SEO implementation

- Every page has:
  - a unique `<title>` and meta description
  - a single `<h1>` and a logical heading order
  - a self-referencing absolute canonical
  - Open Graph/Twitter tags with a 1200×630 image
  - `lang="en"`
- **URLs**: lowercase, hyphenated, trailing slash (`/places/galle/`). Internal links,
  canonicals and the sitemap all use the same form. Static hosts redirect `/places/galle` →
  `/places/galle/`.
- **Structured data (JSON-LD)**:
  - homepage: `TravelAgency` (name, URL, phone, email, locality, area served — all visible
    in the footer) and `WebSite`
  - place pages: `BreadcrumbList` and `TouristDestination` with coordinates
  - tour pages: `TouristTrip`
  - No ratings, reviews, prices or opening hours are claimed.
- `sitemap.xml` lists only indexable canonical URLs. `robots.txt` allows crawling and points
  to the sitemap.
- `404.html` returns a real 404 status on GitHub Pages, Netlify and Cloudflare Pages, and is
  `noindex`.
- Staging and development builds are `noindex` on every page, disallowed in robots.txt, and
  send `X-Robots-Tag: noindex` where `_headers` is supported.
- The map deep link uses a fragment (`/#add=galle`), not a query string, so the homepage keeps
  a single URL.
- `npm run check` fails on:
  - duplicate titles or descriptions, a page without exactly one `<h1>`, a missing robots
    meta tag, or duplicate element ids
  - galleries without alt text, with controls that don't match the photos, or with the
    wrong loading priority; FAQs with empty or repeated questions
  - destination pages missing "Plan a private tour with …", "Nearby places to combine" or
    the planner link for that destination; any `[TODO]`/`TBD` in a page
  - canonical, `og:url`, sitemap or robots disagreements; an indexable page missing from the
    sitemap, or a `noindex` page in it
  - any canonical, Open Graph or JSON-LD URL that isn't on the preferred origin and base
    path; an `og:image` that isn't a real file
  - broken internal links or assets, or a homepage missing a crawlable link to any destination
  - images without `alt` or dimensions, unnamed buttons, invalid JSON-LD, ratings or reviews
    in JSON-LD
- `npm run check:release` adds the launch gate (see "Build modes and safeguards").

## Deployment

The output in `dist/` works on any static host.

- **GitHub Pages**: `.github/workflows/deploy-pages.yml` builds with the `SITE_URL`
  repository variable, runs `npm run check:release`, and only then deploys. It runs
  manually for now; the file explains the one-time setup and how to deploy on push.
  `dist/.nojekyll` is included, and no CNAME file is needed with Actions deployments.
- **Netlify / Cloudflare Pages**: build command `npm run build && npm run check:release`,
  publish directory `dist`, and set `SITE_URL`. `dist/_headers` sets long-lived caching for hashed assets and basic
  security headers. GitHub Pages ignores that file and caches for 10 minutes.
- **Hosting under a sub-path** (e.g. `https://example.com/tours`) works: set `SITE_URL` with
  the path, and every asset, link, canonical and sitemap URL includes it (tested).
  - `robots.txt` must live at the domain root, so add the `Sitemap:` line there.
  - The host must serve `/tours/404.html` for missing pages under the path.

## Changing photos

Put replacement photos in a folder and run `npm run prepare:images -- /path/to/folder`. File
names are mapped in `PHOTO_SOURCES` in `src/data/destinations.mjs`. Alternatively, replace a
file in `src/images/destinations/` directly (1200×800, same name). Adjust `focus` (the
[x, y] focal point) and `alt` for each place in the same data file.

`PHOTO_SOURCES` can also be a Wikimedia Commons file URL: the script downloads the original
(`npm run prepare:images -- --only=<photo name>` processes just that one). Use only photos of
the actual place, without watermarks, under CC0, CC BY or CC BY-SA (never NC or ND), and add the
photographer, licence and source page to `PHOTO_CREDITS` in the same file. The credit then
appears under the photo on the place page and on `/photo-credits/` (linked from every footer),
and `npm run check` fails if it goes missing. Six main photos (Adam's Peak, Arugam Bay, Bentota,
Ella, Hikkaduwa, Nuwara Eliya) were replaced this way in November 2026; see
`docs/research/photos.md`.

## Phones and tablets

The site is laid out for phones first and tested at 320, 375, 390, 430, 768, 1024 and 1440 px.

- **Site menu** (every page): a menu button in the header opens the places by category, the
  experience guides, both services (`/#tour` and `/#transfer` open them directly) and
  contact links. It is a `<details>` element, so it works without JavaScript; `src/js/menu.js`
  adds Escape, closing on an outside click or a link, and no background scrolling while the
  full-screen phone menu is open.
- **Long guides:** an "On this page" list (collapsed) links to every section; guide `##`
  headings get ids in the build, and `npm run check` fails on any in-page link that doesn't
  resolve. Body text is capped at about 70 characters per line.
- **Phone action bar:** on place and experience pages, a slim bar ("Add to your trip" /
  "Ask us") appears once the hero's buttons have scrolled away and hides again at the closing
  "Plan a private tour" band and the footer. Desktop never shows it.
- **Place cards** become a compact row (thumbnail beside the text) under 560 px, and their
  images are requested at thumbnail size there.
- **Touch targets** are at least 44 px on touch screens (larger hit areas where the visual size
  stays the same), and headings scale fluidly with `clamp()` to the same desktop sizes.
- **Planner on small phones:** see [Guided trip planner](#guided-trip-planner). In the review
  step the nights stepper moves under the place name. Opening a place never moves or zooms the
  map; the island is fitted again only when the layout changes (for example when the trip
  drawer first appears).
